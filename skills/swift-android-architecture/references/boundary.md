# The boundary

What goes into shared Swift, what stays on each platform,
and how each app hands its platform services to the shared code.

## Split the package

- **Shared targets** hold models, networking, business logic and view models.
  They import Foundation, Observation and packages that build for Android — nothing else.
- **iOS-only targets** hold everything that touches UIKit, SwiftUI, MapKit, PassKit
  or another platform SDK.
  Polymarket's rule, from its report: anything touching those stayed on the iOS side,
  and the domain logic ended up depending on nothing but Foundation, Observation
  and a small set of portable packages
  (Swift Forums › Our Android app is written in Swift, @poly-rob, 2026-08-04, post 1).
- In a Fuse app, UI modules use SwiftUI through SkipFuseUI;
  that is Skip's ground (`skip-fuse`, `building-skip-ui`).
- **Check every dependency** before relying on it:
  Swift Package Index builds packages for Android and shows the result on each package page
  and in its platforms badge (`sources.md` › Swift Package Index).
  Polymarket names swift-dependencies, swift-clocks, swift-concurrency-extras,
  swift-identified-collections, swift-async-algorithms, swift-crypto and gRPC as working.
- Run `python3 scripts/android_scan.py <root> --route shared-core --shared <Target>`
  to find imports and APIs that will not build for Android.

## Platform services are protocols

Each capability the shared code needs from a platform —
payments, analytics, storage, notifications, authentication —
is a protocol in the shared module, implemented natively by each app
and handed to the shared code when the app starts.

```swift
// typecheck: shared
public enum PaymentResult: Sendable, Equatable {
    case authorized(token: String)
    case cancelled
}

public protocol PaymentsClient: Sendable {
    func requestPayment(amountCents: Int, currency: String) async throws -> PaymentResult
}

public protocol AnalyticsClient: Sendable {
    func track(_ event: String, properties: [String: String])
}

/// Everything the shared code needs from the platform, passed in once at startup.
public struct PlatformServices: Sendable {
    public var payments: any PaymentsClient
    public var analytics: any AnalyticsClient

    public init(payments: any PaymentsClient, analytics: any AnalyticsClient) {
        self.payments = payments
        self.analytics = analytics
    }
}

@MainActor
public final class CheckoutFlow {
    private let services: PlatformServices

    public init(services: PlatformServices) {
        self.services = services
    }

    public func pay(totalCents: Int) async -> Bool {
        do {
            let result = try await services.payments.requestPayment(amountCents: totalCents, currency: "USD")
            services.analytics.track("checkout_finished", properties: ["result": "\(result)"])
            return result != .cancelled
        } catch {
            services.analytics.track("checkout_failed", properties: [:])
            return false
        }
    }
}
```

The iOS app implements the protocol with PassKit in an iOS-only target:

```swift
// typecheck: ios17, continues the block above
import PassKit

final class ApplePayClient: PaymentsClient {
    func requestPayment(amountCents: Int, currency: String) async throws -> PaymentResult {
        guard PKPaymentAuthorizationController.canMakePayments() else { return .cancelled }
        // Build a PKPaymentRequest and present PKPaymentAuthorizationController here.
        return .cancelled
    }
}
```

- **Prefer initializer injection.**
  A `PlatformServices` value passed to the root of the shared code is enough for most apps,
  and it is the easiest to test.
  Polymarket uses Point-Free's swift-dependencies for the same job,
  injecting from the app delegate on iOS and from the `Application` class on Android.
- **Keep the protocol's shape bridgeable:**
  `async throws` functions and value types, no Combine, no closures in collections
  (`bridge-surface.md`).

## The Android implementation

Polymarket's report says its Android implementation is plain Kotlin,
using the Google Pay SDK, conforming to the Swift protocol,
with the Swift `async throws` requirement appearing in Kotlin as a `suspend` function.
skip.dev's Bridging Reference marks protocols as bridgeable
(with function and property requirements, not constructor or static ones),
but does not say that a Kotlin class can conform to one and be passed back to Swift,
and Skip's own bridge tests do not exercise that round trip
(`sources.md`, skip.dev notes).
Treat it as a reported capability: build it, and test the call from Swift into the Kotlin implementation,
before planning around it.

```kotlin
// typecheck: none — Kotlin; the PaymentsClient interface is generated by Skip from the Swift protocol
class GooglePayClient(private val context: Context) : PaymentsClient {
    override suspend fun requestPayment(amountCents: Int, currency: String): PaymentResult {
        // Present Google Pay with the Wallet API and map its result.
        return PaymentResult.cancelled
    }
}
```

The generated Kotlin names and types come from the bridge;
read them from the exported library rather than guessing.
Two rules from skip.dev's Bridging Reference matter for a service protocol:
Swift `Int` arrives in Kotlin as the JVM's 32-bit `Int`,
so amounts that can exceed it need `Int64`;
and mutable structs keep value semantics only toward transpiled Swift,
so hand-written Kotlin should get immutable structs or classes.
If the round trip does not work in your Skip version,
invert it: let Kotlin call a bridged Swift function with the result,
or wrap the Android SDK in a transpiled module bridged to native Swift
(skip.dev › Dependencies).

## What stays where

| Concern | Shared Swift | iOS app | Android app |
| --- | --- | --- | --- |
| Models, decoding, validation | yes | — | — |
| Networking (`URLSession` with FoundationNetworking) | yes | — | — |
| View models and navigation decisions | yes | — | — |
| Screens and navigation containers | — | SwiftUI or UIKit | Compose |
| Payments, maps, wallet passes, push registration | protocol | PassKit, MapKit… | Google Pay, Maps… |
| Logging | a logging protocol or `OSLog.Logger` in Skip modules | — | — |
| Persistence | protocol, or a portable store | — | — |

`OSLog.Logger` reaches Logcat in Skip modules; `print` does not (skip.dev › Debugging).

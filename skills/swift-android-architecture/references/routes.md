# Routes from Swift to Android

Four ways to run Swift code in an Android app, and how to choose.
Versions, sizes and dates live in `versions.md`.
Skip documentation is paraphrased from skip.dev (CC BY-SA 4.0) at the commit named in `sources.md`.

## The four routes

### 1. Skip Fuse app — SwiftUI on both platforms

- **What runs on Android:** the app's Swift, compiled natively with the Swift SDK for Android;
  its SwiftUI is rendered with Jetpack Compose through SkipFuseUI (skip.dev › Lite and Fuse Modes).
- **Shared:** almost everything, including the UI.
- **Bridge:** Skip generates it; Kotlin is written only where the app drops into Compose.
- **Owner:** Skip's skills — `skip-project-creation` to create it, `skip-fuse` for modes and bridging,
  `building-skip-ui` for views.
- **Fits** one Swift team building a new app for both platforms.

### 2. Shared core under native UI

- **What runs on Android:** shared Swift modules compiled natively by Skip,
  exported as Android libraries (`.aar`) and consumed by an Android app written in Kotlin and Compose
  (skip.dev › Project Structure › Creating Separate iOS and Android Apps).
- **Shared:** models, networking, business logic and view models; no UI.
- **Bridge:** Skip generates Kotlin APIs for the shared modules' public surface (`bridge-surface.md`).
- **Owner:** this skill (`boundary.md`, `view-models.md`, `compose-lifetime.md`, `aar-workflow.md`).
- **Fits** an existing Android app or an Android team that writes Compose,
  and products that should look and behave natively on each platform.
  Polymarket's Android app is built this way (`sources.md` › The Polymarket report).

### 3. Skip Lite — Swift transpiled to Kotlin

- **What runs on Android:** Kotlin source that Skip generates from the Swift.
- **Shared:** as in either of the routes above, module by module.
- **Owner:** Skip's `skip-lite-transpilation`.
- **Fits** modules that wrap Android libraries and call Kotlin or Java directly,
  and apps that must be able to leave Skip with readable Kotlin (skip.dev › Lite and Fuse Modes).

### 4. Bare Swift SDK for Android

- **What runs on Android:** a Swift library built with `swift build --swift-sdk …`,
  loaded through JNI — generated by swift-java or written by hand.
- **Shared:** a library behind a small API.
- **Owner:** `swift-android-sdk`.
- **Fits** projects without Skip, and a Swift library added to an existing Android app
  when Skip's project structure is not wanted.

## Choosing between native and transpiled

skip.dev recommends native mode:
"and it is the mode we recommend for most apps" (skip.dev › Lite and Fuse Modes › Native Mode: Skip Fuse),
and, for apps with complex business logic and third-party Swift dependencies,
says Fuse's advantages typically outweigh its disadvantages (same page, Conclusion).
Skip's own agent skills say to default to Lite (`official-skip-skills.md`);
follow the documentation.

| | Native (Fuse) | Transpiled (Lite) |
| --- | --- | --- |
| Swift language and standard library | complete | the transpiler's supported subset |
| SwiftPM packages and C libraries | yes, if they build for Android | only packages written for Skip |
| Calling Kotlin and Java | through the bridge | directly |
| Android app size | larger: the Swift runtime and Foundation ship inside (`versions.md`) | smaller |
| Debugging on Android | no Swift breakpoints in Android Studio; logging, LLDB outside the IDE | generated Kotlin steps in Android Studio |
| Leaving Skip | the Swift stays Swift | readable Kotlin is left behind |
| Build time | slower | faster |

Sources: skip.dev › Lite and Fuse Modes (advantages, disadvantages and conclusions of each mode);
skip.dev › FAQ (debugging).

- A single app may mix modes per module;
  skip.dev expects many apps to combine native logic with transpiled libraries
  that wrap platform services (skip.dev › Lite and Fuse Modes, Conclusion).
- Set `mode` explicitly in every `Skip/skip.yml`.
  The documentation disagrees about the default when it is missing,
  and Skip's source makes it depend on whether SkipFuse is a dependency
  and the module is the primary one (`sources.md`, skip.dev notes).

## Choosing a shared core under native UI over a Fuse app

Choose native UI on Android when one of these holds:

- an Android app already exists, or an Android team will build the UI;
- the product should follow Material conventions on Android rather than mirror the iOS screens;
- the iOS UI depends on UIKit, MapKit, PassKit or other frameworks Skip does not render.

Choose a Fuse app when one Swift team builds both apps and SwiftUI on both is acceptable.
Either way, the shared modules follow the same rules (`boundary.md`, `view-models.md`).

Costs of a shared core under native UI, from Polymarket's report
(an experience report, not documentation):

- an extra export step between a Swift edit and the Android build;
- no Swift breakpoints in Android Studio;
- about 50 MB more at download for their app;
- bridging Swift closures to Kotlin was harder than expected;
- object lifetimes had to be rebuilt on the Compose side (`compose-lifetime.md`).

## Existing apps

skip.dev's advice for an existing iOS app is to start a new Skip project
and move code over module by module, preferring Fuse
(skip.dev › Project Structure › Migrating an Existing App to Skip).
For a shared core, the first step is the package split in `boundary.md`;
Polymarket moved one screen's view model first (Settings) and then the rest, one by one.
